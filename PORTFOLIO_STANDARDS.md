# Portfolio Quality Standards

## Purpose

This repository presents verified work, delivery capability, and collaboration readiness. Every public claim must be supported by code, a live deployment, a reviewable artifact, or a documented release record.

## Case-study structure

Each case study must include:

1. project summary,
2. objective or problem,
3. role and responsibilities,
4. delivery scope,
5. technology stack,
6. implementation approach,
7. quality and release evidence,
8. outcome,
9. limitations and current status,
10. live link or repository link where appropriate.

## Evidence rules

- Do not describe planned functionality as delivered functionality.
- Do not treat generated routes as completed localization.
- Do not claim production status without deployment evidence.
- Do not claim full ownership of work completed by a wider team or tool-assisted workflow.
- Describe leadership, architecture, implementation, QA, and release responsibilities separately.
- Use exact build, route, test, and deployment results when available.
- Keep private repositories private; link the production result instead.

## Project status labels

Use one of these labels:

- Concept
- Prototype
- Internal alpha
- Public preview
- Production
- Archived

## Technical quality baseline

Public frontend work should demonstrate as many of the following as apply:

- responsive behavior,
- accessibility labels,
- typed implementation,
- clear information architecture,
- reusable components,
- locale-aware routing,
- metadata and SEO controls,
- build validation,
- regression checks,
- deployment verification,
- documented limitations.

## Screenshots

Screenshots should show:

- desktop and mobile views,
- important navigation and interaction states,
- representative content,
- no private data,
- no unverified placeholders presented as live systems.

Every screenshot must include a short caption and alt text.

## Writing standard

Portfolio language should be direct and evidence-based. Avoid inflated terms such as “enterprise-grade,” “production-ready,” or “complete platform” unless the available evidence supports them.
